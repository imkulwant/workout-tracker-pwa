# Decisions

Record every ambiguity resolved while implementing `PLAN.md`, and every runtime dependency added outside the plan's stack table.

| # | Date | Decision | Reason |
| --- | --- | --- | --- |
| 1 | 2026-11-14 | Project lives at the repository root, not in a `gym-tracker/` subfolder. | The repository is the project. The `gym-tracker/` root in the plan's tree maps to this repo root. |
| 2 | 2026-11-14 | Work is committed directly on `master`, locally only, one commit per task. | Chosen by Kul for the Phase 0 run. Nothing is pushed without a separate instruction. |
| 3 | 2026-11-14 | Add `@tailwindcss/vite` as a dev dependency alongside `tailwindcss`. | Tailwind 4 integrates with Vite through this plugin. It is build-time only and adds nothing to the runtime bundle. |
| 4 | 2026-11-14 | Keep `vite-plugin-pwa@2.0.0` despite 6 `npm audit` advisories (2 low, 4 moderate) and do not run `npm audit fix --force`. | All trace to `workbox-build` (deepmerge, glob, minimatch), which runs only at build time on our own config. The suggested fix downgrades to `vite-plugin-pwa@1.1.0`, which breaks the plan's "current stable release" rule. Re-check once Phase 2 configures the PWA, and revisit when `workbox-build` ships a patched release. |
| 5 | 2026-11-14 | Pin `typescript` to `~6.0.3` instead of the 7.0.2 the Vite template installed. | `typescript-eslint@8.72.2`, the latest stable, declares peer `typescript >=4.8.4 <6.1.0`. The plan says to use the newest compatible pair. `--force` was rejected because it would run the linter on a compiler it does not support. Revisit when a stable `typescript-eslint` supports TypeScript 7. |
| 6 | 2026-11-14 | Use ESLint (flat config) with `typescript-eslint`, and remove the template's `oxlint`. Enforce layer boundaries with ESLint's built-in `no-restricted-imports`. | The plan specifies ESLint. The built-in rule needs no extra plugin, which keeps the dependency count down. |
| 7 | 2026-11-14 | Accept 6 more `npm audit` advisories from `typescript-eslint` → `typescript-estree` → `minimatch` (12 total: 2 low, 10 moderate). | Same dev-only, build-time class as decision 4: lint tooling matching globs from our own config, never shipped to the device. Re-run `npm audit` at Phase 9 and before release. |
| 8 | 2026-11-14 | Rule 9 is enforced as: `src/app`, `src/ui` and `src/features` may not import `dexie` or `data/db`. They may import `data/repositories` and `data/backup`. | The plan says UI "must never touch Dexie tables directly" but Settings must call the backup functions, which are not repositories. Banning `dexie` and `db` stops direct table access without blocking backup. `dexie-react-hooks` stays allowed for `useLiveQuery` over repository queries. |
| 9 | 2026-11-14 | Repositories reject out-of-range reps (not a whole number from 1 to 999) and weights (outside 0 to 1000 kg) with an `InvariantError`, and round in-range weights to 2 decimals. They never clamp. | The plan states the limits but not the failure mode. Silently changing a stored value is worse than refusing it. `clamp` in `domain/numbers.ts` stays available for UI input handling. |
| 10 | 2026-11-14 | `deleteWorkout` stamps the workout, its workout exercises and its live sets with one shared `deletedAt`. A changed workout date is copied to all of its sets, including soft-deleted ones. `Workout.date` follows `startedAt` unless a date is given explicitly. `finishWorkout` on a completed workout changes nothing. | The shared timestamp lets Phase 5's Undo find what went with a workout. Updating soft-deleted sets stops an undo from restoring a stale date. Idempotent finish survives a double tap. |
| 11 | 2026-11-14 | **Resolved in Phase 3, see row 24.** Unique active exercise names are not enforced in Phase 1. Phase 1 enforces the muscle rules (at least one primary, no primary/secondary overlap) and the in-use rule. "In use" means referenced by a live workout exercise or a live template item. | The plan lists name uniqueness under Phase 3. Deleting a workout frees its exercises for deletion, because only live workout exercises count. |
| 12 | 2026-11-14 | `getPreviousPerformance(exerciseId, beforeWorkoutId)` returns the completed sets of the latest completed workout that started before the given one and has at least one completed set of that exercise, ordered by position. | Matches the plan's "last completed session of that exercise". A workout containing the same exercise twice is not treated specially. |
| 13 | 2026-11-14 | The invariant "only sets with `completedAt` count towards any metric" is enforced by `listCountableSets` in `sets.ts`: ticked sets of completed, non-deleted workouts, filterable by date range and exercise. Phase 7 metrics must read sets through it. It keeps warm-up sets, since excluding them is a metric rule. | Gives the invariant a repository-level enforcement point and tests now, before any metric exists. The plan's definition of a countable set (metrics section) is implemented exactly. |
| 14 | 2026-11-14 | Vitest runs with `TZ=Europe/Stockholm`, and the seed test parses the exercise table out of `docs/PLAN.md` instead of keeping a second copy. | DST behaviour must be tested in the user's zone. The plan's table is the specification (operating rule 5), so the test reads the specification itself. |
| 15 | 2026-11-14 | **Superseded by row 22.** `InstallGate` wraps everything, outside `Boot`, so in a Safari tab no database is opened and nothing is seeded. A `?browser` address flag bypasses it only when `import.meta.env.DEV` is true. E2E tests report Home Screen mode through a fixture that defines `navigator.standalone`, so the real gate stays active in the test build. | A tab does not share storage with the installed app, so seeding or logging there would silently diverge. The bypass exists so the app can be developed in a desktop browser, and `DEV` is false in production builds, which an e2e test confirms. |
| 16 | 2026-11-14 | `Sheet` and `Dialog` are built on the native `<dialog>` element through a shared `ModalShell`. The UI components were verified in real WebKit with a throwaway harness that is not committed. They have no committed component tests yet. | `<dialog>` gives the focus trap, Escape and top-layer stacking for free on iOS 15.4 and later. Component tests would need jsdom and Testing Library, which are not in the plan's stack. Real screens exercise the components in e2e from Phase 3. |
| 17 | 2026-11-14 | Icons and startup images are generated by `npm run icons` (`scripts/generate-icons.mjs`) using Playwright's WebKit. Startup sizes come from Playwright's iPhone device data, for iPhone 12 and newer, which gives 8 sizes. All images are fully opaque. | Needs no image library. Sizes come from device data and not from memory. Re-run the script and paste the printed links into `index.html` when a new iPhone size appears. |
| 18 | 2026-11-14 | `tsconfig.node.json` includes the DOM library. | Playwright's `page.evaluate` callbacks run in the browser and use `indexedDB` and `getComputedStyle`, and the `e2e/` folder is type-checked by this config. |
| 19 | 2026-11-14 | **Superseded by row 23.** `public/_headers` puts only the CSP, `X-Content-Type-Options` and `Referrer-Policy` on `/*`, and no `Cache-Control`. `/registerSW.js` is also `no-cache`, which the plan did not list. There is no `404.html`. `vite preview` serves the `/*` block, so local runs and e2e enforce the production CSP. | Checked against Cloudflare's docs on 2026-11-14: headers from every matching rule are combined, and a duplicate header name is joined with a comma, which would corrupt `Cache-Control`. Without a `404.html`, Pages serves `/` for any non-file path, which gives deep links for free. A stale `registerSW.js` would hold back a new `sw.js` like a stale `sw.js` would. |
| 20 | 2026-11-14 | `vite-plugin-pwa` uses `registerType: 'prompt'` and `injectRegister: 'script'`. The 8 startup images are excluded from precaching, which leaves 14 precached files (393 KiB). The service worker calls `skipWaiting` only on a `SKIP_WAITING` message. | The registration script is an external file because the CSP allows no inline scripts. iOS fetches startup images itself. A new service worker waits for the Update tap that Phase 9 adds, so a release never swaps code during a workout. |
| 21 | 2026-11-14 | Verified, closing the belief in rows 4 and 7: `deepmerge`, `minimatch` and `workbox-build` appear in no shipped file, so the 12 `npm audit` advisories do not reach the phone. The app JS is about 113 KiB gzipped, against the 250 KB target. | Searched every file in `dist/`, with a control string to prove the search works. Re-run `npm audit` at Phase 9 as planned. |
| 22 | 2026-11-15 | The install gate is removed. The app opens directly in any browser tab with no install page, prompt or blocking, and a Home Screen shortcut opens it full-screen like an app (the manifest and iOS tags stay). Also removed: `platform/standalone.ts` and its test, the `?browser` dev flag, `e2e/fixtures.ts` and `e2e/install-gate.spec.ts`. Plan iPhone checklist item 1 is dropped. | Kul's call, overriding the plan's iOS section: most users will use it in a browser, and installing is optional. The cost is known and accepted: a browser tab and the Home Screen app keep separate storage on iOS, so a workout logged in one does not appear in the other. Backup and restore (Phase 6) is the way to move data between them. Launch order is now `ToastProvider` → `Boot` → router. |
| 23 | 2026-11-15 | Hosting is GitHub Pages, as a project site at `https://imkulwant.github.io/workout-tracker-pwa/`, not Cloudflare Pages. The base `/workout-tracker-pwa/` is set in `vite.config.ts` for builds and `vite preview` (override with `BASE_PATH`, for example `/` on a custom domain). The dev server stays at `/`. The CSP and a no-referrer policy are `<meta>` tags injected at build from `csp.ts`. `404.html` is a copy of `index.html`. Deploys run from `.github/workflows/verify.yml` on `master`, after `verify` passes. `public/_headers` and its test are removed. The manifest `id`, `start_url`, `scope` and icons carry the base. E2E tests run against `scripts/serve-pages.mjs`, which behaves like Pages: a path prefix, real 404s, no index fallback and a `max-age=600` cache. Tests navigate with relative paths. | Kul's call after comparing both hosts: it avoids a new account and keeps everything in the repository. Costs, known and accepted: (1) no response headers, so `frame-ancestors` and `X-Content-Type-Options` cannot be set (a meta CSP ignores `frame-ancestors`) and the cache is fixed at 10 minutes, so a new release can be noticed up to 10 minutes late; (2) `imkulwant.github.io` is shared by all of Kul's Pages sites, and storage is per origin, so another site on that origin could read this app's IndexedDB (my reasoning, not checked against a spec); (3) a first-visit deep link gets a 404 status, though the app still loads; (4) moving to a custom domain later changes the origin and needs a backup restore. Verified live that GitHub Pages sends `cache-control: max-age=600`, serves gzip only and returns a real 404 for unknown paths. |
| 24 | 2026-11-15 | Exercise names must be unique among active exercises, ignoring case and edge spaces. Active means live and not archived. The check runs on create, on rename of an active exercise, and on unarchive, inside the same transaction as the write. An archived exercise may share a name, or be renamed to one, until it is unarchived. | Matches the plan ("unique active exercise names, case-insensitively") and its "archived exercises leave the picker". Checking on unarchive stops a restored exercise from silently duplicating a newer one. The transaction means two quick saves cannot both pass. A known gap: if a later seed version adds an exercise whose name a custom exercise already uses, `seedIfNeeded` does not check names. |
| 25 | 2026-11-15 | The plan's "search returns results within 100 ms" is tested as the time from the input event until the filtered rows are in the DOM, not until pixels are painted. Measured on a quiet page: 1 to 7 ms to the DOM, about 17 ms to one painted frame and 33 ms to two. | A first version counted two painted frames and ran in parallel with three other browsers, and read 156 ms. That measured display refresh and machine load, not the search. The pure filter also handles 5,000 exercises inside 100 ms in a unit test. |
| 26 | 2026-11-15 | The exercise picker is hosted on a temporary `/workout` screen (`WorkoutScreen`, marked as scaffolding in the code) that lists what you chose and saves nothing. Phase 4 replaces it. | The plan's e2e test needs the picker to be reachable, but the real workout screen is Phase 4. |
| 27 | 2026-11-15 | Sheets and dialogs focus their title on opening, not their first control. WebKit already does this because the title has `tabIndex={-1}`; the explicit `focus()` call is a guard for other engines and was not tested in any. | `<dialog>` focuses the first control, which in the picker is the search box, and on a phone that raises the keyboard over the list. The title is read out by screen readers and opens no keyboard. |
| 28 | 2026-11-15 | Library body-part chips match exercises by primary muscle, the same rule the plan gives for the calendar heatmap. The form lets the same muscle be picked as primary and secondary and then shows the plan's overlap error, instead of silently preventing it. Archiving asks for confirmation. There is no delete button: the repository can delete unused exercises, but the plan's flow is archive. "Archived exercises stay in history" is verified at the repository level only (`getExercise` still returns them) until the history screens exist in Phase 5. | Keeps the filter consistent across the app, makes the validation rule visible as the plan asks, and protects against accidental removal from the picker. |
| 29 | 2026-11-15 | The app is named **Workout Tracker** everywhere it is shown: the page title, the Home Screen label (`apple-mobile-web-app-title` and the manifest's `name` and `short_name`), the package name, and in the plan the title, the head snippet, the future backup file name `workout-tracker-YYYY-MM-DD.json` and format `workout-tracker-backup`, and the future `localStorage` key `workout.hadData`. The class `GymDb` is now `WorkoutDb`. The in-browser database is still named `gym-tracker`, on purpose. Rows 1, 3 and 5 keep the old `gym-tracker` wording as history. | Kul asked for the name to be consistent. The database name is never shown, and renaming it would make each existing install open a new, empty database and orphan the data in the old one. It can be renamed, at the cost of a one-time reset of data on the phone. `short_name` is now the full name, so iOS may shorten the label under the icon (about a dozen characters fit); that was not tested on a device, and the label can be edited when adding to the Home Screen. |
